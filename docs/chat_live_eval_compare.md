两次都用 `deepseek-chat`，同一套 10 条通用问题，不同会话（同一份样例资料生成的两次工作流）。

| 会话 | 编造编号 | 可核对引用 | 无关请求引用 | 平均上下文 |
|---|---|---|---|---|
| `155c9135` | **0 / 10** | **9 / 9** | 0 | 约 1.7k 字 |
| `6f506305` | **0 / 10** | **8 / 9** | 0 | 约 1.4k 字 |

## 这一轮真正发现的问题：不在模型，在指标和提示词

1. **检测器漏了 `R` 编号**：报告片段是 `R148`，第一版正则只认 `S/P/K` 与 `CODE#1`，
   把大量真实引用判成"未引用"（会话 2 一度只有 3/9）。
2. **把「建议0（P0）」当成证据编号**：报告正文用 `（P0）` 标建议，被误判为编造。
3. **指令里的示例编号被照抄**：为了"要求照抄编号"，我在提示词里写了
   `（S7P1）、（P1-3-1）、REPORT_CHAPTER_MISSING#1` 当例子 —— 模型直接把
   `REPORT_CHAPTER_MISSING#1` 当成可用编号引用了。**示例即候选**，这条要记住。
4. **"可核对"的口径**：只比 `references` 数组会把模型从正文片段里抄来的编号误判成编造；
   正确口径是「上下文正文或 references 里出现过」。

## 结论

- B45 的两个修复（报告正文进检索、强制标注来源）在两个会话上都成立：
  L09 都答对，引用率 8–9/9，编造 0。
- 但两次会话同源（同一份样例资料），**不能说明跨文档泛化**；只是"换一次生成"仍成立。
- 数字在修指标过程中反复变化（9/9 → 3/9 → 8/9），说明**先校准指标，再看模型**。
